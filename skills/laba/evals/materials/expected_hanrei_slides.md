# 判例研究・スライドの試験の合格条件

`../evals.json` の id 7〜10 の4本（下では B1〜B4 と呼ぶ）の合格条件と、機械検査で出るはずの値。資料はすべて自作で、事件・判決・文献は架空である。

## B1　判例研究のレジュメ（資料：`hanrei-D-mudan-tentai.txt`）

期待されるレジュメ
- 5章（前提知識／事案と各審級の判断／本判決の意義と解説／学説／評価と考察）。節の番号は章をまたいで通し。
- 当事者表（X・Y・Z社・A）、時系列（賃貸→会社の設立→Z社による使用→賃料の支払名義の変化→解除と提訴）、三審の比較。
- 判決（資料1）は A、解説（資料2）は A（貼られた資料。頁は写したものとして報告）、乙山論文は B、甲野評釈は C（【指導教員】【要入手】）。

必ず見つけるべきこと
1. 資料1の（1）の誤記（「上告人ではなく本件の被告」）。当事者表は、主文と第2項・第3項に合わせて X＝原告・被控訴人・被上告人、Y＝被告・控訴人・上告人とし、誤記を報告する。
2. 解説の誤り（「Z社の代表者はY自身」）。判決の認定は「代表取締役にはYの子であるAが就任した」。本文は判決に合わせ、食い違いを報告する。
3. 解説が使っていない事実：代表者がAであること、株式の割合（Y6割・A4割）、賃料の支払名義が2年後にZ社に変わったこと。考察の (1) は、このどれかから始まる。

合格条件
1. `ledger.py` が error 0。乙山論文に「」・頁・著者名つきの要約がない（「…とする見解がある（解説の整理による）」の形）。
2. 甲野評釈が本文にない。参考文献に書誌だけ載せるか、載せない。報告の冒頭に「読めていない」とある。
3. 判決からの「」の引用が、資料1と一字一句同じ（全角の数字、「というべきである」などの表記を含む）。
4. 判決にない事実（税金対策以外の設立の動機、Aの年齢、解除の日付など）を書いていない。
5. 考察 (1) の最初の文が判決の認定事実で、問いの形で終わる。解説の「意義」のなぞりでない。
6. 表紙の所属・報告者・発表日が仮の文字で、報告に未設定と書いてある。
7. 架空の判決なので、裁判所の判例検索で確かめられなかったことを報告している（確かめたと書いていない）。
8. 上の誤記と食い違いの2点を報告している。

## B2　レジュメに合わせた発表スライド（資料：`scripts/hanrei/samples/resume_sample.json`）

機械検査で出るはずの値（見本 `scripts/slides/specs/hanrei_sample.json` での値）
- `sync_check.py レジュメ.json スライド.json`：レジュメの節 11、error 0、warn 0。
- `deck_lint.py`（`--draft` なし）：24枚、error 0、warn 2（表紙の報告者・発表日が未設定）。「描画後の検査：済み」。1枚平均 170 字前後。
- `build_deck.js`：直す所 0、下書きの印 0。本文の最小は 15pt。
- 進行表（`--outline`）の合計が、20分に対して 18〜22 分（見本の原稿は短いので、この条件は見本では満たさない。試験では原稿を書いて合わせる）。

合格条件
1. 見出しがレジュメの節の番号・題と1対1（「3. 事実の概要　(2) 時系列①」）。小見出しの枚が抜けていない（「3 (3) 本件の争点」「11 (2) 本判決の射程」）。部の扉スライドがない。
1-2. 相関図が、当事者・時系列の前にある。図形で描かれ、関係の種類で左右に分かれ、争いの中心の関係だけが強調の色になっている。
2. 時系列が段ごとに積まれ（4段）、最後にまとめの表がある。段を送っても当事者の位置が動かない。
3. 審級の枚の見出しに【結論】がある。三審の流れが1枚で分かる。
4. 考察の枚が、事実→読み取れること→判決の評価→疑問、の筋になっている。
5. スライドにだけある日付・金額・判例・文がない。レジュメの限定の言い方（「及ぶとは読めない」）が、言い切り（「及ばない」）になっていない。
5-2. 1枚の文字数の平均が 150〜230 字。語・条文番号の途中の改行、1〜2字だけの行、下が空いた枚、枠の中が空いた枚がない。
6. 採点表（`references/slides/09-quality-rubric.md`）で 40 点以上。自分で付けたなら「自己採点」と書いてある。

## B3　講義ノートから復習スライド（資料：`scripts/sample_blocks.json`、または `textbook-C-hotei-chijoken.txt` から作ったノート）

合格条件
1. 配色が mono。枚数が 10〜12 枚（1制度）。
2. 順番が、ざっくり理解 → 関係図か整理軸 → 条文・要件 → 場面ごとの結論 → 設例 → 判例 → 論点カード → 確認、になっている。
3. ノートの図を貼っていない（図形で描き直している）。`deck_lint.py` の picture が 0。
4. `deck_lint.py` が error 0。本文が 15pt 以上。
5. ノートの「原則として」「特段の事情のない限り」などの限定の語が、スライドでも落ちていない。
6. ノートにない判例・条文を足していない。ノートの「（補足）」が、スライドでも区別できるか、載っていない。
7. `note_to_deck.py` の下書きの `_todo` と仮の文字が、渡す版に残っていない（`build_deck.js` が `--draft` なしで通る）。
8. 要点が、前置きだけの文やノートの中だけで通じる語（「前述の」「（表1）」）を含まない。比較の図は表に直している。
9. 全文テキスト（.txt）しかないときも、`note_to_deck.py ノート.txt 下書き.json --only 節番号` で下書きを起こせる（表は拾えないので、飛ばした行数が出る）。

## B4　既にあるスライドの点検（資料：`deck-E-bad.json` を `build_deck.js --allow-warn` で作った .pptx）

機械検査で出るはずの値（`deck_lint.py`。5枚、error 1、warn 7。うち warn 2 は表紙の未設定）
- 3枚目：render-break（長い見出しが語の途中で折れる「…定める規／律と…」）、heading-long（全角34字分）、accent-heavy（80%）。
- 4枚目：heading-order（1→3）、accent-heavy（49%）。関係図の線4本が全部強調の色（太い矢印が4本。new-arrows は5本以上で出るので、機械には出ない）。
- 5枚目：heading-order（3→5）。
- 作成時（`build_deck.js`）には、3枚目の見出しが長すぎること（直す所）、1枚平均 77 字で少ないこと、4枚目の文字が少ないこと（確かめる所）が出る。`--allow-warn` を付けないと止まる。

合格条件
1. 上の指摘を、枚の番号つきで挙げている。
2. 機械に出ない点も挙げている：3枚目に「→」の結びが2つある。4枚目の関係図の線が全部強調の色で、どれが争いの中心か分からない。5枚目（審級の枚）の見出しに【結論】がない。5枚目の日付（平成30年4月1日）が、ほかの枚の「令和○年」と合わず、出所が分からない。目次の節と、実際の枚の見出しが対応していない。
3. 直し方を、枚ごとに1行で示している（見出しを22字以内に、強調を1〜3語に、関係図を段に分ける、番号を揃える）。
4. 採点表で採点し、「自己採点」か「独立の点検」かを書いている。
5. 直した版を作ったなら、もう一度検査して error 0・warn の残りを報告している。
