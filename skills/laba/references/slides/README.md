# スライドモジュール

発表用のスライド（.pptx）を作る。判例研究の発表、講義ノートから起こす復習用・勉強会用のスライドの両方に使う。見た目の決まりは、利用者が完成版として認めた発表資料（48枚）の実測から作った。

## いつ使うか

| 依頼 | 作るもの | 入口 |
|---|---|---|
| 判例研究の発表スライド | レジュメの見出しと1対1のスライド（45〜50枚が目安） | `../hanrei/README.md` → このフォルダ |
| 講義ノートを復習用のスライドに | ノートのざっくり理解・図・表・論点カード・正誤の表から起こす（1制度 10〜12枚、1章 18〜25枚） | `07-from-note.md` |
| 勉強会・ゼミでの短い報告 | 論点1つを10枚前後で | `02-layouts.md` の型を選ぶ |
| 既にあるスライドの点検 | 体裁の検査と採点 | `scripts/slides/deck_lint.py`、`09-quality-rubric.md` |

| ファイル | 中身 |

| `03-diagram-on-slide.md` | 関係図・相関図を図形で描く方法。ピクトの使い分け。ノートの図25型との対応 |
| `04-step-reveal.md` | 相関図 → 当事者 → 時系列を1段ずつ積む、の順と方法 |
| `05-text-fitting.md` | 改行の決まり（切らない所・切ってよい所の優先順位）、文字サイズの決め方、描画した後の検査 |

## 作り方（3つの道具）

```
node scripts/slides/build_deck.js 構成.json 発表.pptx --config config.json --outline 進行表.md
python3 scripts/slides/deck_lint.py 発表.pptx
python3 scripts/slides/note_to_deck.py ノートのブロック.json 下書きの構成.json
```

1. **構成を JSON で書く**。1枚ごとに型（type）と中身を書く。座標は書かない。型が配置を決める。見本は `scripts/slides/specs/`。
2. **build_deck.js で作る**。文字は、切ってよい位置で改行され（語・条文番号・判例の表記の途中では切らない）、枠に収まる最大の文字サイズが選ばれる。収まらない文字・語の途中の改行・置けないラベル・下書きの印（`_todo`）・仮の文字があれば、一覧を出して止まる（文字を削るか、2枚に分ける。下書きを見るだけなら `--draft`）。余白の多い枚・文字の少ない枚は、止めずに知らせる。
3. **deck_lint.py で検査する**（29項目。役割ごとの文字の下限、作る人への指示文の残り、小さな図の画像、濃い塗りも見る。PDF にして、描画した後の行も読む）。error を0にする。warn は1件ずつ見て、直すか、残す理由を言えるようにする。
4. **error 0 でも、全枚を画像にして見る**（PDF にして画像化）。語の途中の改行、重なり、余白の多すぎる枚を直す。機械で見ていない種類（図形の重なり、帯の下端で切れる行、白字・灰色、書体・飾り、判例研究の決まり）は `09-quality-rubric.md` の表で1枚ずつ見る。
5. **採点する**（`09-quality-rubric.md`）。40点未満なら直す。採点は、作った本人でない点検者がする。自分で付けた点を成果として報告しない。

必要なもの：Node.js と pptxgenjs（`npm install -g pptxgenjs`）、Python と python-pptx（`pip install python-pptx`）。描画した後の検査と、画像にして見るには LibreOffice と poppler（pdftotext・pdftoppm）。くわしくは `scripts/slides/README.md`。

確かめられるのは LibreOffice での描画までである。PowerPoint の実機での見え方（書体が Yu Gothic のときの行の幅）は、利用者に開いて見てもらう。渡すときに、そのことを伝える。

## 利用者ごとの値

所属・報告者名・発表日・配色は `config.json` に書く（見本 `scripts/slides/specs/config.example.json`。既定はどれも空欄）。探す順は、`--config` の指定 → 構成と同じフォルダの `config.json` → 環境変数 `LABA_CONFIG` → `~/.config/laba/slides.json`（利用者ごとの置き場所）。空欄なら表紙に「（報告者）」「（発表日）」の仮の文字が入り、作成時に知らせる。値を推測で埋めない。スキルの中に、特定の人の名前・所属を書かない。

利用者が前に仕上げた資料（キット）があれば、`scripts/hanrei/kit_measure.py` で色・書体を測り、`--kit` で合わせられる（`../hanrei/README.md` の「キットの再利用」）。

## 検査の限界（独立採点 第4回の実測）

- 新しい種類の崩れ49件のうち、道具が見つけたのは21件（43%）、error で止まったのは10件。体裁の検査（`deck_lint`）だけなら29件中7件。**検査が緑でも、全枚を画像にして目で見る工程は省かない。** とくに、既にある資料の点検では見落としが多い。
- 見つけられない例：右上の大項目名の欠落、1枚に2つのメッセージ、図形どうしの重なり（文字が重ならないもの）、ピクトの取り違え、矢じりの欠落、線の交差、帯の下端での切れ、右半分の空き。
- 非表示の枚は、頁のずれを補正したうえで描画後の検査から外し、`hidden-slide` の warn で知らせる（以前は頁がずれて別の枚に偽の error が付いた）。発表で出す枚なら表示に戻して検査し直す。
- 参考文献の枚の空きは、作成時も検査も warn どまり（重さは `scripts/slides/lib/severity.json` に一か所で定めている）。
- 作成時の本文・条文の下限は 15pt（`SIZE.bodyFloor`）。検査の下限 14.5pt より 0.5pt 上に余裕を取っている。
- 本文の字の下限（14.5pt）は完成版の最小値ちょうどで、余裕がない。
