# 講義ノートからスライドを起こす

laba の講義ノートは、スライドにしやすい部品でできている。ざっくり理解は導入の1枚に、図は図形の関係図に、表はそのまま表に、設例は請求→抗弁→再抗弁の1枚に、論点カードは1論点1枚になる。ノートを作ったあとで「これを復習用のスライドにして」「勉強会で説明したい」と言われたら、この手順で起こす。

## 1. 対応

| ノートの部品（ブロック） | スライドの型 | 起こし方 |
|---|---|---|
| 表紙（題・副題） | cover | kind を「復習スライド」「勉強会資料」に |
| この回の全体像（ざっくり） | zakkuri か points | 最初の1枚。3行に縮める |
| 章の見出し（H） | section（大項目名） | 扉スライドは作らない |
| 節・小見出し（S・SS） | 各スライドの見出し | ノートの番号（「12-3-1」）があればそのまま使う。なければ通し番号を振る |
| 「発展」の小見出し | （載せない） | 復習用では省く。入れるなら `--with-advanced` |
| ざっくり理解（ZH、または「ざっくり理解：…」の小見出し＋Z・ZB） | zakkuri | 場面／何が困るのか／そこで／ひとことで、に振り分ける（「困るのは」「そこで」「ひとこと」の語が手がかり） |
| 整理軸の表・座標図 | axis | 2×2 に収まるとき。収まらなければ compare_table |
| 条文の説明 | statute | 条文＋要点（◎）＋「設例では」 |
| 定義 | definition | |
| 本文の段落（P） | points | 段落の主題文だけを拾い、1点2行までに縮める |
| 判例（4段） | case_ref | 事案／判断／→ 設例との関係。理由は原稿（ノート欄）へ |
| 判例の一覧表 | case_matrix | 6行×4列まで。超えたら分ける |
| 比較表・区別表（T） | compare_table | 列を4つまでに絞る |
| 当事者関係図（F） | relation、timeline | 貼らずに図形で描き直す。図題の「この図で分かること」を下の1行（key）にする |
| 比較の図・対応の図（F。図題に「比較」「対比」「違い」「整理」） | compare_table の雛形 | 関係図にしない。比べる観点を行、比べる対象を列に |
| 時間軸の図（F） | time_axis | 起算点・期間・満了を、出来事と期間に分けて書く |
| 場合分けの流れ図（F） | branch | 問いを3つまでに |
| 流れ図（F） | instance_flow、issues | 箱を5個までに |
| 設例（請求・抗弁・再抗弁） | yoken | 各段2行まで |
| 結論（K） | conclusion | 言い切りの1〜2行＋理由 |
| 論点カード（KD、または論点・問題の所在・規範の列を持つ表） | ronten_card | 1論点1枚。各欄2行に削る |
| 正誤の表（命題・正誤・根拠の列を持つ表） | tf_check | 3問で1枚。誤りの箇所を根拠の行に残す |
| 確認の問い（記述式） | qa | ノートの設問と答えから |
| 索引の表、短答・論述の対応表、文章の表（1セル 120 字超） | （載せない） | ノートで見る表。下書きの報告に「飛ばしたもの」として出る |

## 2. 手順

1. **下書きを作る**：`python3 scripts/slides/note_to_deck.py ノート 下書き.json`。型を当てはめた構成の下書きができる。直す所には `_todo` が付き、型の内訳、飛ばしたもの、枚数が目安を超えたかどうかが表示される。

   | 渡すもの | 読めること | 読めないこと |
   |---|---|---|
   | ブロックの JSON（`build_docx.py` の入力）・DOC を定義した .py | 全部（見出しの階層、ざっくり理解、表、図題、論点カード） | — |
   | 出来上がった .docx | 番号つきの見出し、段落、表（そのまま）、「図n」の図題 | 番号のない見出しの階層（短い段落を見出しとみない） |
   | 全文テキスト（.txt。`--text-out` の出力や、貼り付けたテキスト） | 番号つきの見出し（「12-3-4　…」）、「ざっくり理解：」、段落、「図n」の図題、「 \| 」区切りの表 | 空白区切りの表（表らしい行は飛ばして、行数を知らせる） |

   - 手元にブロックの JSON があれば、それを渡す。なければ .docx、それもなければテキストを渡す。
   - 道具が自動で当てはめるのは、章・節の見出し、ざっくり理解、本文の段落（1つの見出しにつき1枚、段落の要の1文を4件まで）、表（比較表・論点カード・正誤の表を見出し行で見分ける）、結論、判例（C＋P2）、図（図題の語から型を選んだ雛形）まで。
   - つなぎ・予告・評価の紹介だけの文（「以上のとおり，…」「もっとも，…問題も指摘されている」「…応答が考えられる」）は要点にしない。段落にほかの文があれば、そちらを拾う。冒頭の「以上のとおり」「このように」「もっとも」「なお」は外す。
   - 段落から拾う1文は、前置きだけの文を避ける。「第2は，上訴である。たとえば…」は「上訴：…」の形にする。「前述の」「（⇨…）」「（表1）」「（12-3-4-2）」「（補足）…」のような、ノートの中だけで通じる語は外す。
   - 長い見出し（全角20字超）は、親の見出しと重なる部分を外す（「12-3-4-1　同時審判申出共同訴訟の意義」→「12-3-4-1　意義」）。親の見出しは、右上の大項目名に出る。
   - 図は、図題の語で型を選ぶ（比較・対比・違い・整理・見比べ・左右 → compare_table、流れ・手続・順 → instance_flow、場合分け・分かれる → branch、期間・時効 → time_axis、そのほか → relation）。どれも雛形で、仮の文字（「（…を書く）」）が入っている。25型すべての対応は `03-diagram-on-slide.md` の6。
   - 条文（statute）の文言は、ノートから写さず、e-Gov 法令検索（https://laws.e-gov.go.jp/）で、発表の時点で施行されている条文を開いて写す。見出し（［ ］の中）も e-Gov の表記に合わせ、改正で新設・変更された条は「（平成29年改正で新設）」のように書く。e-Gov で確かめられなければ statute の枚を作らず、条文番号と要旨だけを points に書く。4行を超える条文は、本件にかかわる項・号だけを載せる。
   - 整理軸（axis）、条文（statute）、設例（yoken）、時間軸（time_axis）、場合分け（branch）は、下書きの points・compare_table・relation を見て、人が型を選び直す。
   - 1章が長いノートは、`--only 12-3` や `--only 12-3-4` のように章・節を番号で絞って作る（その番号と、その下の節だけが入る）。1章まるごとを掛けると、復習用の目安（18〜25枚）の3倍ほどになる。
   - 正誤の問いを別のファイルで持っているなら `--tf 正誤.json` で末尾に足す。問いだけの枚にするなら `--hide-answers`。
2. **削る**。下書きには、ノートの文がそのまま入っている。ノートの1節（数百字）は、スライドでは1枚（100〜200字）になる。残すのは、主題文、条文番号、結論、強調する語。理由の詳しい説明は、原稿（ノート欄）に移す。
3. **図を図形に直す**。`_todo` の付いた relation の枚に、当事者と関係を書く（`03-diagram-on-slide.md`）。ノートの図の画像は貼らない。
4. **順番を組み替える**。スライドは、ノートより「先に全体、後で細部」にする。

   | 順 | 枚 |
   |---|---|
   | 1 | 表紙 |
   | 2 | ざっくり理解（何の話か、なぜ要るか） |
   | 3 | 関係図か整理軸（全体の地図） |
   | 4〜 | 条文・要件 → 場面ごとの結論（表） → 設例（yoken） → 判例 |
   | 終わり | 論点カード → 正誤の確認（tf_check）・確認の問い（qa） → まとめ |

5. **作って検査する**：`build_deck.js` → `deck_lint.py` → 全枚を画像で見る。下書きの印（`_todo`）と仮の文字が残っていると、`build_deck.js` と `deck_lint.py` は止まる。途中の出来を見るだけなら、どちらにも `--draft` を付ける。`--draft` で作ったものは渡さない。
6. **採点する**（`09-quality-rubric.md`）。

## 3. 配色

ノートから起こしたスライドは、mono の配色（黒・灰・強調1色）を既定にする。ノートの図と色が揃い、白黒で刷っても読める。発表で映すなら teal にしてよい（`--theme teal`）。

## 4. 正確さを保つ

スライドは短くするので、限定の語や確度の語が落ちやすい。本体の規則（`../added-text-safety.md`）を、スライドにも当てる。

- 「原則として」「特段の事情のない限り」「〜と解されている」を落とさない。落とすと、結論が言い過ぎになる。
- 判例の結論を1行にするとき、判決の射程より広く書かない。
- ノートで「（補足）」とした内容は、スライドでも「（補足）」と分かるように書くか、載せない。
- 判例の書誌は、ノートで確かめたものだけを写す。スライドで新しく判例を足さない。
- 図形で描き直した関係図は、ノートの図と同じ関係だけを描く。

## 5. 分量の目安

| ノート | スライド |
|---|---|
| 10頁前後（1制度） | 10〜12枚 |
| 20頁前後（1章） | 18〜25枚 |
| 30頁以上 | 章ごとに分けて作る |

## 6. 実際のノートで試した結果（下書きの出来）

1章分の講義ノート（ブロック 169 個：段落 83、表 14、図 6、ざっくり理解 4）に掛けたときの結果。下書きがどこまで使え、どこから人の手が要るかの目安になる。

| 指定 | 枚数 | `_todo` | そのまま作成したときの検査 |
|---|---|---|---|
| 指定なし（1章まるごと） | 79 | 59 | error 2（文字が多すぎる表）、warn 6 |
| `--only 12-3 --tf 正誤.json`（1節＋正誤 30 問） | 28 | 22 | error 0、warn 3（文字が多い） |

- ざっくり理解は、4つとも zakkuri に振り分けられた。場面の文が長く、削る必要がある。
- 表 14 個のうち、比較表として使えたのは 6 個。論点カードの表は 12 枚の ronten_card に、正誤の表は 10 枚の tf_check になった。判例の理由を文章で書いた表（1セル数百字）と索引の表は飛ばした。
- 段落から拾った要点は、1文目がそのまま入るので、ほぼ全部に「長い」の `_todo` が付く。ここが一番手の掛かる所である。
- 図 6 枚は、どれも描き直しの雛形になる。型の選び直し（座標図は axis、判例の一覧は case_matrix）は人がする。

全文テキスト（.txt）から、1節だけを起こしたとき（`--only 12-3-4`）：7枚（zakkuri 1、points 4、compare_table の雛形 1、ほか）、`_todo` 6 件、空白区切りの表らしい行 40 行を飛ばした。ざっくり理解は4欄とも拾えた。表（要件の表、控訴の表）は拾えないので、表も起こすならブロックの JSON か .docx を渡す。

下書きは、枚の順番と型の当たりを付けるためのものである。仕上げの品質は、削る・描き直す・組み替えるの3つで決まる。

## 7. 見本

`scripts/slides/specs/note_review_sample.json`（法定地上権、10枚、mono、1枚平均 190 字前後）。ざっくり理解 → 関係図 → 条文と要件 → 場面ごとの成否 → 設例 → 参考判例 → 論点カード → 確認の問い → まとめ、の順になっている。
