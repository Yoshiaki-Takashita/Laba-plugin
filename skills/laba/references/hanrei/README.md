# 判例研究モジュール

一つの判決を取り上げ、報告用のレジュメ（Word）と発表スライド（PowerPoint）を作るときに使う。講義ノート（laba の本体）とは目的が違うので、手順も分けてある。

## 講義ノートとの違い

| | 講義ノート（本体） | 判例研究（このモジュール） |
|---|---|---|
| 素材 | 利用者が渡す資料（レジュメ・教科書） | 判決の原文と、利用者が渡す解説（評釈・調査官解説など） |
| 目的 | 資料を漏れなく、分かりやすくする | 一つの判決を、事実から読み、自分の見方を述べる |
| 網羅の基準 | 資料の見出し・判例・条文 | 判決文の事実・各審級の判断 |
| 読者 | 利用者本人 | 指導教員と演習の参加者（引用元を知っている人たち） |
| 中心の危険 | 足した説明が誤りを生む | 読んでいない文献を書く、判決にない事実を書く |
| 成果物 | Word のノート | Word のレジュメ＋発表スライド |

共通する規則は本体のファイルをそのまま使う。判例の確認は `../case-verification.md`、条文は `../statute-verification.md`、足した説明の扱いは `../added-text-safety.md`、設例を論じる型は `../yoken-jijitsu.md`。判例を紹介する4段（事案の型／結論／判決が挙げる理由／批判・射程）は `../techniques.md` のとおりで、判例研究ではこれを審級ごとに、原文の引用つきで厚く書く。

## 最初に聞くこと（1回だけ）

対象の判決が分かっていれば、すぐ調査を始める。同じ返信で次をまとめて聞く。

- 手元にある解説の全文（判例集の解説、調査官解説、評釈）。貼ってもらえれば原文として引ける。
- 発表日、発表時間、レジュメの頁数の目安。
- 所属・演習名・報告者名を表紙に入れるか（`config.json` に書く。空なら仮の文字を入れて知らせる）。
- 前に仕上げた判例研究（レジュメ・スライド・作ったスクリプト）があるか。あれば渡してもらい、体裁を合わせる（下の「キットの再利用」）。
- 指導教員の著作のうち、この判決に触れているものがあるか（あれば必ず原文で確かめる。`02-citation-grade.md` 4）。

## 利用者ごとの値（config）

スキルの中には、特定の人の名前・所属・演習名を書かない。利用者ごとの値は `config.json` に書く。既定はどれも空欄で、空欄なら表紙に「（報告者）」などの仮の文字が入り、作成時に一覧が出る。値を推測で埋めない。

| 項目 | 例（書き方の例。既定は空欄） | 使われる所 |
|---|---|---|
| `year` | `"2026年度"` | レジュメの表紙の右上 |
| `affiliation` | `"○○大学法学部専門演習（○○ゼミ）"` | レジュメ・スライドの表紙 |
| `presenter` | `"（報告者の氏名）"` | レジュメ・スライドの表紙 |
| `date` | `"2026.10.○○"` | レジュメ・スライドの表紙。未定なら空欄のままにし、渡すときに伝える |
| `note` | `"条文番号は特に断りのない限り現行民法による。"` | レジュメの表紙の注 |
| `chapter_break` | `true` | 章ごとに改頁するか（既定は改頁する） |
| `theme` | `"teal"` | スライドの配色 |

置き場所と、探す順：

1. 作成時の `--config` の指定
2. 構成（JSON）と同じフォルダの `config.json`（その案件だけの値）
3. 環境変数 `LABA_CONFIG` が指すファイル
4. `~/.config/laba/hanrei.json`（レジュメ）・`~/.config/laba/slides.json`（スライド）。利用者ごとの値を一度書いておく場所

見本は `scripts/hanrei/samples/config.example.json` と `scripts/slides/specs/config.example.json`。同じ利用者の2件目からは、聞き直さずに 4 を使う（発表日だけは毎回確かめる）。

## キットの再利用

利用者が、前に仕上げた判例研究一式（レジュメの .docx、発表スライドの .pptx、それを作ったスクリプト）を「キット」として渡すことがある。前回の体裁に合わせるために使う。

1. **受け取る**。フォルダか zip で渡してもらう（個々のファイルでもよい）。版が複数あれば、名前の番号がいちばん大きいものを使う。
2. **測る**：`python3 scripts/hanrei/kit_measure.py キットのフォルダ --out kit_profile.json`。レジュメの余白・文字サイズ・書体・表の罫線・引用段落・参考文献の大きさ、スライドの色・書体・文字サイズの分布・1枚の文字数・ピクト・枠線を測り、LABA の既定との違いを一覧にする。測るのは寸法だけで、本文や氏名は取り出さない。
3. **決めてもらう**。違いの一覧を利用者に見せ、「前回に合わせる」か「LABA の既定にする」かを聞く。違いがなければ聞かない。
4. **合わせて作る**：`resume_build.py … --kit kit_profile.json`、`build_deck.js … --kit kit_profile.json`。レジュメは余白・文字サイズ・書体、スライドは色・書体が合う。合わせたくない項目は、`kit_profile.json` の `apply` から消す。
5. **部品を使う**。`kit_profile.json` の `scripts` に、キットのスクリプトの関数名が出る。図や表を描く関数など、今回も使えるものがあれば、中身を読んで確かめてから使う（このツールはスクリプトを実行しない）。前回の事件に固有の文字・座標が入っている関数は、そのまま使わない。
6. **構成と分量も合わせる**。前回のレジュメの頁数、スライドの枚数、1枚の文字数（`kit_profile.json` の `pptx.measured`）を、今回の目安にする。
7. キットの中身（事件の文、氏名、所属）を、スキルのファイルや見本に写さない。

キットがなければ、LABA の既定（完成版として認められた資料の実測）で作る。

## してはいけないこと

- 判決文にない事実・金額・日付を書く。
- 読んでいない文献を、読んだように書く（「」・頁・著者名つきの要約）。
- 未確認の印（【要確認】）、下書きの印（`_todo`）、仮の文字（「（役割）」「（…を書く）」）、作業の記録を、渡す版に残す。道具は、これらが残っていると止まる。`--draft` を付けて作ったものは渡さない。
- スライドに、レジュメにない内容を足す。レジュメの限定の言い方を言い切りに変える。
- 利用者が自分の言葉に直した段落（です・ます、太字、下線）を、次の版で書き直す。

失敗の型は `failure-catalog.md` にまとめた。
