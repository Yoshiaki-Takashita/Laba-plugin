# 手順の詳細（12段階）

入口の SKILL.md の流れを、段階ごとに「入力・すること・出力・通過の条件」で書く。段階を飛ばしてよいのは、該当するものが無いときだけ（設例の無い資料に⑧は要らない）。

## 目次
- 0. 資料の型を見分ける
- ①取り込み　②一覧化　③文体の測定　④構成　⑤本文　⑥ざっくり理解　⑦図表　⑧設例　⑨機械検査　⑩独立点検　⑪採点　⑫渡し方
- 型ごとの分岐（教科書型／レジュメ型／設例中心型／資料なし）
- 改訂の回し方

## 0. 資料の型を見分ける

最初に資料がどの型かを決める。型で④以降の書き方が変わる。

| 型 | 見分け方 | 本文の体 | 重点 |
|---|---|---|---|
| 教科書型 | 文章で論証している。段落がある。`style_profile.py` が `textbook` と出す | 資料と同じ体（多くは、である調） | 文体の模倣、難所の図、判例の4段 |
| レジュメ型 | 箇条書き・体言止め・矢印が中心。文章が少ない | です・ますの解説（既定値） | 前提の加筆、行間を埋める、問いへの答え |
| 設例中心型 | 事例と設問が中心（演習・ケース検討） | レジュメ型と同じ。設例の部分は論証の型で | 請求→抗弁→再抗弁、結論の言い切り |
| 資料なし | 題目だけ渡された | です・ますの解説 | 判例・論点の一覧を先に作る。網羅に限界があると伝える |

一つの資料に複数の型が混ざることは多い（解説＋演習事例）。その場合は部分ごとに型を当てる。

利用者が「この資料の言葉を使って」「精度が高いのでこれを重視して」と言ったら教科書型として扱い、用語・論理・書誌を資料に合わせる。「これ単体だと分かりにくいので解説を足して」と言ったらレジュメ型として扱い、前提の加筆を厚くする。

## ① 取り込み

- 入力：PDF、テキスト、画像（頁の写真・画面の写し）。
- すること
  - PDF は文字の抽出（pdftotext -layout）と、頁の画像化の両方を行う。図・表・当事者関係の図は文字の抽出では崩れるので、画像を必ず目で見る。
  - 画像は頁順を確かめる（頁番号は画像の端に印字されていることが多い。届いた順と頁順は一致しないことがある）。見開きは左右に切り分け、小さい字（コラム、脚注）は拡大して読む。
  - 作業用の書き起こしテキストを作る（頁ごと）。これは検査（一致・網羅・文体）に使う作業ファイルで、成果物には入れない。
  - 資料が複数の単元を含むなら、全部を扱う。扱わない部分があるなら、理由と一緒に利用者に伝える。
- 出力：`work/source.txt`（書き起こし）、頁の画像。
- 通過の条件：全頁を読んだ。読めなかった箇所（つぶれた字、切れた行）を控えた。

## ② 一覧化

- すること：`scripts/inventory.py work/source.txt --out work/inventory.json --md work/inventory.md` を走らせ（文体の測定 ③ も同じ回に走らせてよい。互いに独立）、出てきた一覧を目で補正する。機械は見出しとコラムを取りこぼす。
- 一覧に入れるもの：全見出し（コラム・囲み記事を含む）、全判例（書誌）、全条文、全相互参照、全ての問い（「答えよ」「説明しなさい」「〜か」）、資料の図表。
- あわせて書くもの：「文章だけでは分かりにくい点」を3つ以上（⑥⑦の置き場所になる）。資料の誤記と思われる箇所（⑫で報告する。本文で黙って直さない）。
- 通過の条件：一覧を見れば、資料を開かなくても「何が書いてあるか」の骨組みが分かる。

## ③ 文体の測定

- 教科書型：`scripts/style_profile.py work/source.txt --out work/profile.json`。数値と、判例・学説・例示の決まった言い回しを控える（`style-imitation.md`）。
- レジュメ型・資料なし：測らない。既定値（です・ますの解説）で書く。
- 通過の条件：本文をどの体で書くか、読点はどちらか、決まった。

## ④ 構成

- ノートの見出しを資料の見出しと1対1で対応させる。順序も資料のとおり。コラムは「発展：○○」の見出しで、該当する節の中に置く。
- 表紙の直後に「この回の全体像（ざっくり）」。各章の頭に、その章を貫く整理軸か「前提」。まとめは最後に1か所（全体のまとめ）。章ごとの要点は、巻末の論点カード（`ronten-card.md`）に置く。資料が短い（10頁未満）ときは、論点カードは省いてよい。
- 迷う判断は `algorithms/` の決定表で決める（資料の型、表か文か、判例の置き場所、ざっくり理解の置き場所、補足の札）。
- 設例があれば、設例の章の頭に「前提：請求・抗弁・再抗弁」（刑事・行政・憲法はそれぞれの型。`yoken-jijitsu.md`）。
- 分野の定番の整理軸・混同しやすい概念・図が効く難所は `fields/` の該当ファイルを読む。
- 出力：ブロックの骨組み（見出しだけの JSON か Python モジュール）。

## ⑤ 本文

- `techniques.md` の技法で書く。教科書型は `style-imitation.md`、足した説明は `added-text-safety.md` を守る。
- 判例は書く前に確認する（`case-verification.md`）。確認できないものは、資料に書かれた範囲にとどめる。確認は、条文・判例・文献を**まとめて呼ぶ**（`speed.md` 2、`scripts/verify_plan.py` で組に分ける）。
- 問いには、すべて太字の「答え」を付ける。
- 長い条文の列挙は表にする（号／場面／なぜ）。
- 資料の範囲外は「範囲外補足」として1段落まで。

## ⑥ ざっくり理解

- ②で書き出した難所の直前に置く（`zakkuri.md`）。章ごとに機械的に置かない。
- 本文の理由の列挙を繰り返さない。本文は同じ設例を「前述の設例において」で受ける。

## ⑦ 図表

- 難所ごとにメッセージを一文で書き、型を選ぶ（`figures.md`、`algorithms/figure-type.md`）。`scripts/figgen/specs/` の用例を写して中身を入れ替え、`figgen/cli.js` で作る。`fig_lint.py` で error 0、`figgen/trace.py` で本文と照合し、PNG を目で見る。図が何枚もあるときは `figgen/cli.js batch 仕様… --outdir DIR --png` で1回に作り、`fig_lint.py` と `trace.py` も全部の図を1回で渡す。エンジンにない形のときだけ `scripts/templates/` のひな形を手で直し、`fig_build.js` で PNG にする。
- 図の照合表（図の要素→本文の根拠）を作業ファイルに書く。根拠のない要素は消す。
- 表は、並べると分かるものだけ。判例は本文か表の一方にだけ書く。

## ⑧ 設例

- `yoken-jijitsu.md` の型で論じる。各ケース・各設問の最後に太字の「結論」。末尾に結論一覧表。
- 資料が結論を示していない所は、ノートとしての結論を示し、その旨を書く。

## ⑨ 機械検査

`scripts/build_docx.py` で docx と本文テキストを出し、`scripts/pipeline.py` を走らせる（`run_checks.sh` は基本の検査だけを回す簡易版）。`pipeline.py` は互いに独立な検査を同時に走らせる（結果は順に走らせたときと同じ）。**`scripts/build_and_check.py` は、docx の作成・PDF 化・全部の検査を1回の呼び出しで回す**（PDF 化と検査が重なる）。

```
python3 scripts/build_and_check.py work/blocks.json --out work --source work/source.txt \
    --figs 'work/figs/*.svg' --default-law 民事訴訟法 --cards work/cards.json --tf work/items.json
```
下の `pipeline.py` の例の引数は、`--note`・`--body`・`--blocks`・`--out`・`--pdf` を除いて、そのまま渡せる。

```
python3 scripts/pipeline.py --note NOTE.txt --body BODY.txt --out work/checks --source work/source.txt \
    --blocks blocks.json --figs 'figs/*.svg' --cards cards.json \
    --reasons reasons.json --fulltext work/fulltext --tf items.json --default-law 民事訴訟法 \
    --coverage-ignore ignore.json --certainty-ignore certainty_ignore.json
```
レポート `work/checks/report.md` に、検査の結果、機械の採点、「9.5 に届く条件のうち未達」、「次に直す点」が出る。次に直す点の決め方は `algorithms/next-fix.md`（16指標の決定表）、指標ごとの手順は `metrics/`。段階ごとの確認表は `checklists/`。

| 検査 | 指標 | 通過の条件 |
|---|---|---|
| 網羅（inventory、coverage_check） | ⑬ | 欠落 0（機械の誤検知は `--coverage-ignore` に理由を書いて除く） |
| 文体（style_profile、style_check） | ⑯ | WARN 0 |
| 置き換え・浮いた語（word_swap_check） | ⑯⑩ | 置き換えの型 0、資料に出ない語 0、出にくい言い回し 0 |
| 一致（match_check） | ⑩ | 生の値と除外後の値の両方を控える。除外後で最長30字以下・12字一致率10%以下 |
| 確度（certainty_check。全文と、層つき） | ④ | 「見当たらない」を一件ずつ見て、落としていれば戻す。足した層の候補 0（別の点の文は理由を書いて除く） |
| 書誌（cite_check） | ② | 所見 0 |
| 条文（statute_check） | ① | 一覧を現行の条文と1件ずつ照らす（`statute-verification.md`）。食い違いの候補を読む |
| 要件・効果（yoken_table --check） | ①⑫ | 所見を読む（効果の言い切り、同じ条文で向きの違う効果） |
| 定義（definition_check） | ⑤ | 照合表を1行ずつ読む。定義なし 0、ノートの中の食い違い 0 |
| 判例の理由の出所（reason_source_check） | ③ | 所見 0 |
| 理由の出所表（reason_table check。`--reasons`） | ③ | 判決文未確認 0、抜き書きの不一致 0、所見 0 |
| 論証の型（argument_check） | ⑥ | 足した層で理由のない塊 0。地の文全体が資料の−1ポイント以内（合格は−3ポイント以内） |
| 密度（density） | ⑥⑦⑨⑪ | 具体例密度が資料比1.1以上。重複率 3%以下 |
| 情報効率（info_efficiency） | ⑪ | 分量は資料の1.15倍以内（巻末の表を除く。上限1.3倍）。削る候補 0 |
| まとめの重複（summary_dup_check） | ⑪ | WARN 0。言い直しの層 4%以下 |
| 相互参照と対比（xref_index） | ⑨ | 資料の ⇨ の欠落 0、参照のない語 0 |
| 論点カード（card_build。`--cards`） | ⑫ | 所見 0。答案での使い方の欄（短答・書き出し）あり |
| 短答式の命題（tf_items check。`--tf`） | ⑫ | 所見 0（確度の注意は、読んで理由を書いたものだけ除く） |
| 図（fig_lint。`--figs`） | ⑧ | error 0 |
| docx | — | 検証を通る。PDF にして全頁を目で見る |

機械が見るのは形だけである。通っても、法的な正確さ・意味のずれ・書き手の判定は分からない（次の段階の独立点検で見る）。機械の誤検知を除くときは、必ず理由を残す（除いた項目と理由は、各検査の出力に残る）。

## ⑩ 独立点検

本文を書いていない点検者に、3種の点検をさせる（`verification.md`。指示文のひな形は `reviewer-prompts/`）。点検の種類は互いに独立なので、**同時に頼む**（Cowork・Claude Code では、`agents/` の点検の担当を同じ回に立てる。`orchestration.md`）。チャットでは担当を立てられないので、`verification.md` 6 に従う。自分で照合しただけのものは「未実施」と書く。点検者の指摘のうち記憶に基づくものは、原典で確かめてから直す。

## ⑪ 採点

点検者の採点（`reviewer.json`）と機械の結果を `scripts/score.py` に入れ、総合点と判定を出す（`scoring.md`）。次に何を直すかは `algorithms/next-fix.md`。指摘を直して⑨〜⑪を回すのは**既定で最大2回**（`speed.md` 5。3回目は優先度1の所見が残るときだけ）。利用者が「資料を上回るまで」「9.5 まで」と求めたときに限り、判定が出るまで（目安は2〜4回）回し、さらに各指標を9.5まで上げたいときは、`scoring.md` 5 の表と `metrics/` の各ファイルの「9.5 に届く条件」を1項目ずつ満たす（機械の条件と、点検者の採点の両方が要る）。

## ⑫ 渡し方

`delivery.md` の型で報告する。版番号を上げ、前の版を残す。

## 型ごとの分岐

### 教科書型
1. ②の一覧を厚く作る（網羅の土台）。
2. ③で文体を測り、⑤は資料と同じ体で書く。用語・判例の書誌は資料の表記。
3. 付加価値は⑥⑦で出す。本文は、資料の難しい文を噛み砕く所だけ手を入れる。
4. ⑨の一致検査を必ず見る。文体を合わせると丸写しに近づくので、術語以外は自分の言葉に戻す。

### レジュメ型
1. 行間を埋める。箇条書きの各項目を「何か→なぜか→ただし」の文章にする。
2. 章の頭の「前提」を厚くする（その制度を理解するのに必要な仕組み）。
3. 資料が「判例」とだけ書く箇所は、判例を特定して補い、補ったことを報告する。
4. 資料の図は描き直す（画像を見て、当事者・権利・時間の流れを読み取ってから）。

### 設例中心型
1. 設例の事実を図にする（当事者関係、時間軸）。
2. 論証の型を先に置き、段階ごとに「要件→当てはめ→結論」。
3. 小問ごとに結論を言い切り、末尾に一覧表。

### 資料なし
1. その分野で必ず出る判例と論点の一覧を先に作り、検索で裏を取る。
2. 判例ごとに「対になる判例」、制度ごとに4欄（条文上の要件／解釈上の要件／審理・手続の特則／不服申立てでの扱い）を埋める。
3. 判決効・対抗力などは、効力の範囲を例ごとに書く。一般化しない。
4. 網羅には限界がある（標準的な事項でも抜ける）ことを、渡すときに伝える。資料をもらえれば精度が上がることも伝える。

## 改訂の回し方

- 直すのは指摘された箇所だけ。直した結果、前の版で有益だった文が消えていないかを確かめる。
- 体を変える改訂（です・ます→である）は、語の置き換えで済ませない（`style-imitation.md`）。
- 改訂のたびに⑨を走らせ直す。数値は走らせ直した値だけを書く。
