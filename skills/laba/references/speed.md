# 速く進める

LABA は段階が多く、チャット（claude.ai の会話）で全部を順に回すと時間がかかる。ここは、**正確さの守りを減らさずに**待ち時間を減らす決まりである。時間の大半は、(1) 条文・判例を1件ずつ確かめる往復、(2) 図や検査を1本ずつ走らせる往復、(3) 直しと採点の回しすぎ、の3つにある。

## 目次
1. 動いている場所で分担が変わる　2. 確認は「まとめて呼ぶ」　3. 道具は「まとめて走らせる」　4. 速さ優先（軽い依頼）　5. ⑨〜⑪の回数の上限　6. 速くしても省かないもの　7. 測った値と見込み

## 1. 動いている場所で分担が変わる

| 場所 | 担当（`agents/`）と hooks | 進め方 |
|---|---|---|
| claude.ai のチャット | **読み込まれない**（無いものとして進める） | 1人で進める。同じ回に道具の呼び出しをまとめる（2）。道具は一括で走らせる（3） |
| Cowork、Claude Code | 読み込まれる | 担当に分けて同時に進める（`SKILL.md`「担当に分けて進める」、`orchestration.md`）。確認・図・検査の一括は、ここでも使う |

見分け方：担当を立てる道具（Agent／Task）が使えるなら Cowork か Claude Code。無ければチャットとして進める。チャットでは、独立点検の担当を立てられない。そのときは `verification.md` 6（独立点検は未実施と報告する）に従う。

## 2. 確認は「まとめて呼ぶ」

条文と判例の確認が、チャットでは一番長い。1件ずつ呼んで結果を待つと、件数だけ往復する。**互いの結果を要らない呼び出しは、同じ回に全部出す。**

1. 先に一覧を作る（1回の道具の実行で）：`inventory.py`（資料の判例・条文）、`statute_check.py`（ノートの条文）、`verify_plan.py`（同じ条・同じ判例を1件にまとめ、**法令名つきの表記**で1件ずつ並べ、組に分ける）。
2. **1回目**：条文は `law_get_article` を条文ごとに、判例は `case_verify_citation` を判例ごとに、文献は `biblio_search` を文献ごとに、**同じ回に一緒に出す**。コネクタは同じ上流への呼び出しを自分で順番に処理するので、まとめて出しても取り違えない（待つ時間は、1件ずつ呼ぶより短い）。
3. **2回目**：1回目で `found` の判例について、`case_get`、理由を書く判例の `case_get_fulltext`（`find`）、「」で引く箇所の `case_quote_check` を、また同じ回に全部出す。
4. **3回目**：`no_match`・`multiple`・`upstream_error` だけ、入力を直して引き直す。
5. コネクタが無いとき（ウェブで確かめる）：e-Gov と裁判所のように**サイトが違う呼び出しは同じ回に**出す。同じサイトへは、一度に3件までにする（サイトを止めないため）。
6. 1回に出す数は、20件前後を目安にする。`upstream_error` が増えたら半分にして引き直す。コネクタ側の同時数の上限は**不明**。

まとめて呼ぶ前に必要なもの：呼び出しの入力が、結果に頼らず決まっていること。たとえば `case_get_fulltext` は、判例が見つかったあとでないと呼べない。これは次の回に回す。

確認の結果は、1件ずつ文に書き起こさず、**表1枚**（条文・判例ごとに、ツール・status・出所の URL・取得日時）にまとめる（`connector.md` 5）。

## 3. 道具は「まとめて走らせる」

道具の呼び出しも、1本ずつ呼ぶと往復が増える。次は、結果を変えずに一度で済ませる使い方である。

| したいこと | 使う道具 | 同時になること |
|---|---|---|
| 検査を全部 | `scripts/pipeline.py`（`--jobs N`。既定は CPU の数、最大 8） | 互いに独立な検査（約22本）を同時に走らせる。順に走らせたときと、各ファイルの中身は同じ |
| 簡易の検査 | `scripts/run_checks.sh` | 独立な検査を背景で同時に走らせ、出力は元の順 |
| 図を何枚も | `node scripts/figgen/cli.js batch 仕様1.json 仕様2.json … --outdir DIR --png`（`all` も同じ） | SVG を先に全部作り、PNG を同時に N 枚（既定は CPU の数）。誤りのある仕様は飛ばして残りを作る |
| 手書きの SVG を PNG に | `node scripts/fig_build.js a.svg b.svg … --outdir DIR` | PNG を同時に変換 |
| 図の検査 | `fig_lint.py 図1.svg 図2.svg …`（1回の呼び出しに全部）、`figgen/trace.py 仕様…`（同） | もともと複数を1回で受ける |
| docx・検査・PDF | `scripts/build_and_check.py BLOCKS --out DIR …` | docx を作ったあと、PDF 化と全部の検査を同時に走らせる（頁数の検査だけが PDF を待つ） |

使い方の例（⑦の図を全部、⑨を1回で）：

```
node scripts/figgen/cli.js batch work/figures/*.json --outdir work/figures --png
python3 scripts/fig_lint.py work/figures/*.svg --out work/figs.json
python3 scripts/build_and_check.py work/blocks.json --out work --source work/source.txt \
    --figs 'work/figures/*.svg' --fig-specs 'work/figures/*.json' --default-law 民法
```

`--jobs 1` を付けると1本ずつ走る（速さだけが変わる。何かおかしいときの切り分け用）。

## 4. 速さ優先（軽い依頼）

次のすべてに当てはまる依頼は「速さ優先」で進めてよい。利用者が「急ぎ」「ざっと」「速く」と言ったときも、下の条件のうち**軽さ**（主題・分量）を満たすなら同じ扱い。

- 主題が1つ（1制度・1論点・1判例）。
- 資料が短い（目安：5,000字以内、または10頁未満）。
- 図が3枚以内。判例が5件以内。

| 段階 | 速さ優先での扱い |
|---|---|
| ①② | 省かない（取り込みと一覧は網羅の土台）。道具は1回の実行で |
| ③ | レジュメ型・資料なしは測らない（元からそう）。教科書型は測る（道具は一瞬） |
| ④ | 見出しは資料と1対1のまま。概念の整理軸は1つ |
| ⑤ | 省かない。判例・条文は、書く前に**まとめて確認**（2）。判例は、理由を書くものだけ全文まで当たり、ほかは書誌と結果まで |
| ⑥ | ざっくり理解は難所の直前に置くが、数は最大3か所 |
| ⑦ | 図は3枚以内。**まとめて作る**（3）。機械の点検と本文との照合は省かない。六観点の採点は省き、PNG を1回目で見て矢印を読み上げる |
| ⑧ | 巻末は縮約：論点カード5つまで、短答10問まで。判例の理由の出所表は、本文に書いた判例について付ける（省かない） |
| ⑨ | `build_and_check.py` を1回。直すのは優先度1・2の所見だけ |
| ⑩ | チャット：独立点検は立てられない → 「独立点検は未実施」と報告（省略ではなく、できないこと）。Cowork・Claude Code：法的点検と足した文の点検の2つだけ同時に |
| ⑪ | 採点は機械の値を1回だけ。「資料を上回る」の判定は出さない。回さない |
| ⑫ | 報告に「速さ優先版」と書き、縮約した所（巻末・ざっくり理解・図の採点・点検）を列挙する |

速さ優先にしないもの：複数の主題、分量の大きい資料（10頁以上）、判例研究（別の流れ。13段階）、採点を頼まれたとき、利用者が正確さを最優先と言ったとき。迷ったら通常の手順。

## 5. ⑨〜⑪の回数の上限

「資料を上回るまで回す」を、既定では次のように抑える。

| 版 | 回す回数（機械検査→直し→再検査） | 3回目をやる条件 |
|---|---|---|
| 通常 | **最大2回**（1回目：作ったあと。2回目：優先度1・2を直したあと） | 2回目のあとにも、優先度1（誤りにつながる）の所見が残るとき、または点検者が重大・中程度の誤りを挙げたとき。優先度3以下では回さない |
| 速さ優先 | **1回**（直しは優先度1・2を直すだけで、再検査は直した箇所に限る） | 優先度1が残るとき |

- 3回回しても優先度1が残るなら、止めて、残りを報告に書く（直し続けない）。
- 利用者が「9.5 まで上げて」「採点して」と言ったときだけ、`workflow.md` ⑪の「9.5 に届く条件」まで回す。
- 直した結果、前の版で有益だった文が消えていないかは、回数にかかわらず確かめる（`workflow.md` 改訂の回し方）。

## 6. 速くしても省かないもの

どの進め方でも省かない。

- 条文の確認（コネクタか e-Gov）と、判例の確認（コネクタか裁判所）。確認できなければ「未確認」と書く。
- 確認していない判例の理由を［判示］と書かない。もっともらしい理由を作らない。
- 足した説明の規則（「（補足）」、理由を述べる文、確度の語を強めない、限定語を落とさない）。
- 資料の網羅（機械の照合）と、資料の誤記の報告。
- 機械の検査の実行（速くするのは走らせ方で、検査の数や基準ではない）。
- 報告で、省いた段階・走らせなかった検査・未実施の独立点検を正直に書く。

## 7. 測った値と見込み

### 7.1 スクリプトの時間（実測。`evals/bench/bench.py` で再現できる）

測った環境：CPU 4 個、Python 3.11、Node 22、sharp あり。見本は自作の架空の資料（`evals/bench/`）。各 3 回の中央値。数値は計算機と負荷で変わる。

| 対象 | 前（順に・1本ずつ） | 後 | 倍率 |
|---|---:|---:|---:|
| `pipeline.py`（検査20本。本文840字） | 0.87 s | 0.27 s | 3.2 倍 |
| `pipeline.py`（検査20本。同じ見本を12回つないだ本文1万字） | 0.97 s | 0.33 s | 2.9 倍 |
| 図45本を SVG と PNG（600dpi）に：1本ずつ呼ぶ | 12.2 s | 2.3 s（`batch`・同時） | 約5倍 |
| 同：まとめて呼ぶが順に（`--jobs 1`） | 6.1 s | 2.3 s | 2.7 倍 |

検査は1本ずつが短い（数十ミリ秒）ので、全体の時間は起動の回数で決まっている。実際の36頁のノートでは、検査1本が長くなるので、倍率は計算機の CPU の数に近づくはずだが、**未測定（不明）**。図の PNG は変換が重く、同時に走らせる効果が大きい。

### 7.2 Claude 側の往復（見込み。測ったものではない）

条文20件・判例10件・図5枚・「」で引く箇所8か所の通常のノートを仮定し、**道具を呼ぶ回（往復）**を数えた見込み。1回の往復の長さは環境で違うので、時間に直していない。

| 作業 | 前（1件ずつ） | 後（まとめて） |
|---|---:|---:|
| 条文20件の確認 | 20 回 | 1 回（20件を同時） |
| 判例10件の確認（書誌・要旨・全文） | 約 30 回 | 2 回（1回目：書誌10件。2回目：要旨・全文を同時） |
| 「」の照合8か所 | 8 回 | 2回目に含む（0 回の追加） |
| 引き直し（no_match など） | 約 5 回 | 1 回 |
| 図5枚（作る・点検・照合・PNG） | 約 20 回 | 3 回（batch、lint、trace） |
| docx・検査・PDF | 3 回 | 1 回（build_and_check） |
| ⑨〜⑪の回し（既定の回数） | 2〜4 回（約 3 回で約 24 往復） | 2 回（約 16 往復） |
| **合計** | **約 110 回** | **約 25 回** |

前の列は、`connector.md` と `statute-verification.md` の旧い手順（1件ずつ）と、`workflow.md` の「回す回数の目安は2〜4回」に従った場合の見込み。後ろの列は、この文書の手順に従った場合の見込み。実際は、`no_match`・`upstream_error` の数と、利用者の資料で変わる。**これは見込みであり、実測ではない。**

Cowork・Claude Code で担当に分けたとき（5節の担当）は、節の執筆・確認・図が同時に進むので、本文の執筆の待ち時間が、節の数ぶんの1人に近づく。ただし、親が担当へ渡す・結果を読む往復と、担当ごとの読み込みで、トークンの使用量は増える（**増えた量は未測定**）。
