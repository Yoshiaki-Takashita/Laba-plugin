# P1 範囲・P2 構成（`outline.json`）と本文の形

## 1. 範囲（扱う概念・外すもの）

1. **資料つき**：資料にある概念・数・例を全部拾い、資料にないものは扱わない。拾った項目を `outline.json` の各節の `facts` に、資料の語のまま短く書く（後で担当が自分の分だけ読む）。
2. **単語・分野**：`scope.md` のとおり、標準の章立てを確認先つきで立て、概念の地図 `map.json` を作る（概念 5〜15・前提の向き・外すもの）。節の `terms` は地図の概念から取り、`todo`（確かめていない）の概念は定義しない。1 節に新しい概念は 2〜4 個まで。**単語の題では、その語そのものを第 1 章第 1 節で定義する**（前提の概念・前史は、事例か総説の 1〜2 文で触れるだけにし、前史だけの節を先に立てない）。**構成を先に決め、根拠は後で当てる**：節ごとに、その節が答える問い（`question`）と段落の設計（`paras`。下の 2b）を書いてから、段落の主張ごとに根拠を確かめる（根拠の表 `work/ch<n>/facts.tsv`・`sources.md` 2b）。根拠の取れない段落は設計から外す。節の `facts` には、確かめた主張を台帳の ID つきで短く書く（例：`"換気温度は作物ごとに違う [R02]"`）。項は `writer-brief.md` 2b の節の型の順に立てる。

## 2. 構成の規則（数は教科書の測定から。`textbook-prose.md` §1・§2）

- 階層は **章 → 節 → 項**。番号は書かない（紙面では GNOTO が付ける）。
- 節の題は 8 字前後（20 字まで）、項の題は 5 字前後（8 字まで）。**名詞で止める**（「〜について」「〜とは」で終えない）。
- 1 節は本文 1,200〜1,600 字・項 2〜4 個。
- 各節は **事例（具体）→ 総説（定義・分類）→ 要件・手順 → 例外・比較** の順で開く。事例の枠は節の頭（見出しの直後）に置く。事例の無い題（現象の説明・年表）は、具体の場面の 1〜2 文から入る。
- 図は「言葉より図が速い所」に 1 節 1 つまで。選び方は `figure-judgment.md`（判断の 12 行）。型は `flow`・`tree`・`table`・`matrix`・`timeline`・`concept`・`relation`・`compare`・`chart`・`scale`（laba-textbook `figure-spec.md`）。まだ描けない型（scene・venn・family・ledger）に当たったら `want` に残す。図を描くのは本文の後（`figures.md`）。図にしない所に図を置かない。
- 太字にする語（定義する用語）を節ごとに 2〜6 個決め、**同じ語を 2 つの節で定義しない**（担当表）。

## 2b. 節の問いと段落の設計（`question`・`paras`）

段 L5 の盲検の採点で読みやすさが下がった理由は「段落に論点が混ざる」「題から外れる・細部が多い」だった。書く前に、段落ごとに言うことを 1 つずつ決める。

- `question`：この節が答える問いを 1 文で（単語の題の第 1 節なら「〈語〉とは何で、何のためにあるのか」の形）。
- `paras`：本文の段落を順に並べる（事例の枠・補足・要点・図は数えない）。1,200〜1,600 字で 5〜7 個。各段落は：
  - `role`：**前提 → 定義 → 要件 → 例 → 例外** の順（`比較` は例外の位置。同じ役割が続くのはよい。後ろの役割から前に戻らない）。前提＝場面・なぜ問題になるか（事例の枠を受ける）。定義＝何の一種で何が違うか。要件＝条件・しくみ・式・効果。例＝事例への当てはめ・典型の例。例外＝成り立たない場合・限界・似た概念との違い。
  - `point`：この段落の 1 論点（1 文・60 字まで）。「と」「や」で 2 つの論点をつなぐなら段落を分ける。
  - `answers`：この段落が `question` にどう答えるか（1 文）。**書けない段落は、題から外れているので外す**（前史・隣の制度・発展の話・細かい年や数だけの段落）。
- 検査：`book_state.py outline` が役割の順・空の欄を誤りにし、数と長さを注意で出す。

## 3. `outline.json` の形

```json
{"chapter": {"no": 1, "title": "温室の管理"},
 "sections": [
  {"id": "s1", "title": "換気の基準", "chars": 1400,
   "items": [{"title": "上限温度"}, {"title": "開度"}, {"title": "例外"}],
   "case": true, "terms": ["換気温度", "開度"],
   "question": "温室はいつ、どれだけ窓を開けて温度を下げるのか",
   "paras": [
    {"role": "前提", "point": "室温が上がりすぎると作物が傷むので換気で下げる", "answers": "なぜ窓を開ける基準が要るかを示す"},
    {"role": "定義", "point": "窓を開け始める室温を換気温度と呼ぶ", "answers": "「いつ」開けるかの基準を定める"},
    {"role": "要件", "point": "換気温度は作物の種類によって違う", "answers": "基準が一つではないことを示す"},
    {"role": "要件", "point": "開く幅（開度）は上回った温度に応じて大きくする", "answers": "「どれだけ」開けるかに答える"},
    {"role": "例", "point": "事例の温室で換気温度と開度を当てはめる", "answers": "基準の使い方を具体で確かめる"},
    {"role": "例外", "point": "外気が低すぎる日は開度を抑える", "answers": "基準どおりに開けない場合を示す"}],
   "fig": {"kind": "flow", "why": "温度が上がって窓が開くまでの順序"},
   "facts": ["室温が換気温度を超えたら天窓を開ける", "例：換気温度28度・開度は1度ごとに10%"],
   "excluded": []}
 ]}
```
`case`＝事例の枠を置くか。`question`・`paras` は 2b。`fig` は無ければ `null`。P5 で図にしたら `"id": "f1"`、やめたら `"dropped": "理由"` を足す（まだ描けない型は `{"kind": "table", "want": "venn", ...}`）。検査：`python3 ${CLAUDE_PLUGIN_ROOT}/skills/laba-book/scripts/book_state.py outline outline.json`。

## 4. 本文の形（役割の印つき Markdown。節ごとに 1 ファイル）

```
# 節の題
:::box
事例（3 文以内・約 120 字・人物は A・B）
:::
総説の段落（空行で区切る。定義する用語だけ **太字**）

## 項の題
本文の段落
:::aside
補足（1〜2 文。読み飛ばしても論がつながる内容だけ）
:::
:::fig id=f1 kind=flow
図が示すこと（1 行。P5 で図にしたときだけ。id は figs.json の図）
:::
:::point
- 要点（3〜5 項目・1 項目 27 字まで）
:::
```
- `#` は節、`##` は項。`:::point` は節に 0〜1、`:::aside` は 0〜3。本文に箇条書きを使わない（要件の番号だけは段落の中で ①②）。
- 事例の枠の前は見出しか別の事例の枠だけ（本文の途中に挟まない）。
